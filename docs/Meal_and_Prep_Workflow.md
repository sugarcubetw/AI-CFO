# 餐點選擇與備料流程

## 1. 目的

讓接待人員在辦理入住時快速確認早餐時段與餐點，系統顯示餐點歷史並協助檢查多日住宿不重複，由接待人員決定實際餐點；所有入住辦理完成或每日 18:00 產出次日備料表。

本文件只定義規格，尚未實作。

## 2. 已確認條件

- 方糖民宿目前有 4 道餐點。
- 一般首次、單日住宿的預設餐點為鮭魚。
- 同一筆多日住宿在餐點數量足夠時不得重複。
- 多日住宿或二訪住客可在同一早餐日期吃與其他住客不同的餐點。
- 餐點輪替由接待人員決定；系統只提供建議、歷史與重複警示。
- 原則上同一訂單、同一早餐日期的住客使用相同餐點；個別飲食需求可例外。
- 接待人員可在入住時逐早餐日期選擇餐點。
- 接待畫面可快速新增餐點。
- 早餐時段為：
  - 08:00
  - 08:30
  - 09:00
  - 09:30
  - 10:00
  - 不用餐
- 次日備料表在以下任一條件先發生時產出：
  1. 當日所有預計入住訂單均完成接待。
  2. 每日 18:00。
- 使用者後續提供每道餐點對應的備料項目與用量。

## 3. 餐點主檔

| 欄位 | 說明 |
|---|---|
| `meal_code` | 永久識別碼，不因改名變更 |
| `meal_name` | 顯示名稱 |
| `is_default` | 是否為預設餐點；同時只能一筆 |
| `is_active` | 是否可供選擇 |
| `display_order` | 接待畫面的顯示順序，不代表自動輪替 |
| `dietary_tags` | 過敏原、葷素及禁忌標籤 |
| `recipe_version` | 備料版本 |
| `effective_from/to` | 生效期間 |
| `prep_mapping_status` | complete、incomplete、retired |

初版主檔：

| 代碼 | 餐點 | 狀態 |
|---|---|---|
| `MEAL-SALMON` | 鮭魚 | 已確認、預設 |
| `MEAL-WAGYU-RICE` | 和牛燒飯 | 已確認 |
| `MEAL-EGGS-BENEDICT` | 班尼迪克蛋 | 已確認 |
| `MEAL-VEGETABLE-POT` | 雜菜煲 | 已確認 |

## 4. 接待畫面

每個早餐日期顯示一列：

| 日期 | 時段 | 人數 | 系統建議餐點 | 接待選擇 | 飲食例外 |
|---|---|---:|---|---|---|
| 2026-08-02 | 08:30 | 2 | 鮭魚 | 單選 | 無 |
| 2026-08-03 | 08:30 | 2 | 班尼迪克蛋 | 單選 | 不吃牛 |

操作要求：

- 早餐時段必選，預設不自動選時間。
- 選「不用餐」時，早餐人數設為 0，該日不安排餐點。
- 一般首次、單日住宿預選鮭魚；多日或二訪住客顯示歷史餐點及未重複候選，接待人員可一鍵選擇。
- 同一訂單同一天原則上使用同一主餐；個別過敏或禁忌以「替代餐／例外」記錄。
- 多日訂單一次顯示所有早餐日期，避免逐日切換畫面。
- 同一供餐日期可同時存在多種餐點，備料表必須依實際選擇分別彙總。

## 5. 餐點選擇與不重複規則

1. 只使用生效且啟用的餐點。
2. 一般首次、單日住宿預設鮭魚，除非禁忌衝突或接待人員更改。
3. 多日住宿與可辨識的二訪住客，系統顯示本次及歷史餐點；接待人員選擇實際餐點。
4. 系統不得自行決定輪替順序，只能將未使用且無禁忌衝突的餐點列為優先候選。
5. 同一住宿在可用餐點數量內不得重複；接待人員仍可覆寫，但須填寫原因並保留稽核紀錄。
6. 禁忌或過敏衝突的餐點從候選清單排除或明確警示。
7. 住宿早餐日超過可用餐點數量時：
   - 由接待人員選擇可重複的餐點。
   - 優先避免連續兩天相同。
   - 在接待畫面提示「餐點數量不足以全程不重複」。
8. 同一天不同訂單可使用不同餐點；不可用「全館當日餐點」覆蓋個別已確認選擇。

## 6. 快速新增餐點

接待人員可輸入餐點名稱快速新增，但新餐點先建立為：

```text
is_active = true
prep_mapping_status = incomplete
recipe_version = null
```

規則：

- 可立即選給住客。
- 必須顯示「尚未設定備料」警示。
- 備料表將該餐點列入「未完成備料映射」，不可靜默省略。
- 完成食材、單位與每份用量設定後才轉為 `complete`。
- 餐點名稱修改不影響歷史訂單；刪除改為停用。

## 7. 備料主檔

使用者提供資料後，每道餐點建立：

| 欄位 | 說明 |
|---|---|
| 餐點 | 鮭魚 |
| 食材／備料項目 | 待提供 |
| 每份用量 | 待提供 |
| 單位 | 克、顆、片、份等 |
| 備料損耗率 | 選填 |
| 採購包裝量 | 選填 |
| 提前準備天數 | 選填 |
| 注意事項 | 解凍、醃製或過敏原 |

計算原則：

```text
需求量 = 確認供餐份數 × 每份用量
含損耗需求量 = 需求量 × (1 + 損耗率)
```

精確計算由規則引擎完成，不由 AI 自由推算。

## 8. 備料表產出

### 8.1 產出時機

- 每當「今日所有預計入住訂單已完成接待」時，若早於 18:00，產出次日備料表草稿。
- 每日 18:00 強制產出／更新次日備料表，不受未完成入住阻擋。
- 18:00 後新增或修改用餐資料時，產生新版並列出差異。

### 8.2 版本狀態

```text
DRAFT → FINAL_AT_18 → REVISED
```

- `DRAFT`：所有入住提前完成後產生，可繼續更新。
- `FINAL_AT_18`：18:00 的正式備料基準。
- `REVISED`：18:00 後有變更，須通知廚房／工作群組。

### 8.3 備料表內容

1. 供餐日期與版本時間。
2. 各用餐時段總人數。
3. 各餐點份數。
4. 飲食禁忌、過敏與替代餐。
5. 依餐點彙總的食材及備料需求。
6. 房號／訂單對照，僅顯示工作必要資料。
7. 尚未完成接待的訂單。
8. 尚未建立備料映射的餐點。
9. 相較前一版的新增、取消與變更。

## 9. LINE 通知

18:00 訊息範例：

```text
[明日早餐備料｜2026-08-03｜18:00版]
08:00：2 位
08:30：4 位
09:30：2 位

鮭魚：4 份
和牛燒飯：2 份
班尼迪克蛋：2 份
替代餐：1 份（過敏提醒）

未完成接待：1 筆
備料映射缺漏：0
```

18:00 後修改時只發差異：

```text
[早餐備料異動｜第 2 版]
新增：09:00 鮭魚 2 份
取消：08:30 和牛燒飯 1 份
請依新版備料表調整。
```

## 10. 驗收條件

- 單日訂單預設鮭魚。
- 2～4 個早餐日的訂單，在無禁忌衝突時不重複。
- 超過 4 個早餐日時顯示不可全程不重複警示，且不連續重複。
- 同一天可同時分配鮭魚及其他餐點，且不得互相覆蓋。
- 二訪住客可查閱先前餐點歷史，由接待人員選擇不同餐點。
- 系統不自動決定輪替順序；接待人員是最終決定者。
- 選「不用餐」後不產生餐點與備料需求。
- 接待人員可一次完成多日餐點選擇。
- 快速新增餐點可立即選用，但備料映射缺漏必須出現在備料表。
- 所有接待完成可提前產生草稿；18:00 一定形成正式版本。
- 18:00 後的異動形成新版本及 LINE 差異通知。
- 備料合計可追溯至日期、時段、餐點與訂單。

- `TBC-MEAL-006`：「所有入住完成」是否以當日預計入住訂單為範圍。
- `TBC-MEAL-007`：18:00 備料表的 LINE 群組與接收角色。
- `TBC-MEAL-009`：二訪住客的穩定識別鍵（PMS 客戶 ID、電話雜湊或其他方式）。
